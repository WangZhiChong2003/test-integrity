# Test design review guide

Use this reference when creating or reviewing a nontrivial test. It expands the workflow in `../SKILL.md`; it is not a checklist that must be exhaustively executed for every small change.

## Choose a trustworthy oracle

A test oracle is the source of the expected answer. Prefer, in context:

- A documented API or protocol contract.
- A known-answer fixture independently checked against a standard or trusted reference.
- An invariant or mathematical property (for example, encoding then decoding returns equivalent content).
- A separately developed reference implementation, when its independence is real.
- An intentionally recorded regression case with a demonstrated failure before the fix.

Weak oracles include expected data generated by the function currently under test, copied production expressions, and snapshots of incidental formatting with no specified contract.

## Check for false confidence

Ask whether the test would fail if the relevant functionality were broken. Common mistakes:

- Assertions are never reached because the loop processes zero elements.
- A mock returns the expected result without calling meaningful production logic.
- The test checks only absence of exceptions where result correctness matters.
- The expected result duplicates the same bug as the implementation.
- An overly broad exception handler treats test setup failures as success.

## Check for brittleness

Ask whether the test would still pass after a valid refactor:

- Private helper calls, stack frames, cache representation, or internal container order are usually not public contracts.
- Exact log text and error wording should be asserted only when they are explicit user-facing requirements.
- File ordering or parallel scheduling should be asserted only where ordering is guaranteed.
- Correctness assertions should not depend on an arbitrary runtime threshold on shared CI hardware.
- Randomness, clocks, locale, time zone, file paths, and environmental dependencies should be controlled where relevant.

## Right-size the test

- Prefer the lowest level that exercises the relevant behavior without mocking away the risk.
- Use integration tests for interactions that unit tests cannot meaningfully capture.
- Preserve a small number of end-to-end checks for critical flows, rather than duplicating every internal combination.
- Add boundary cases based on reachable states and actual contracts, not all imaginable inputs.
- Do not require introducing new production error handling to satisfy an impossible test setup.

## Situations that legitimately require internal tests

Internal structure can itself be contractual in systems software: memory layout, synchronization ordering, ABI, wire format, persistence guarantees, lock-free properties, and performance budgets may be required behavior. Assert these when backed by a real requirement; distinguish them from implementation accidents.

## Small example: stable parsing test

**Fragile:** Assert that `Parser.parse()` calls `_scan_tokens()` exactly twice.

**Durable:** Given a documented valid input, assert the parsed fields and stable error behavior for an invalid input.

**Important exception:** If the internal call count is itself an established performance or protocol requirement, test it explicitly with an explanation of that contract.
